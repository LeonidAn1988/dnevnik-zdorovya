# Полное ревью: сохранность, восстановление, семейный обмен

Дата: 17 октября 2026. Проверяемый исходник: `60db05d31ddb6f28cbf6090abbe748da9c3d2410`.

Независимый критик: persistence. Production-код не менялся. Настоящий телефон, медицинские записи, ключи и облако не использовались. Воспроизведения выполнены в отдельном Chromium с `hasTouch: true`, настоящим IndexedDB и поддельным транспортом облака. Android использует тот же `webStorage` (`src/platform/capacitor/index.ts:31`); это проверка общего кода, а не доказательство воспроизведения на физическом Android.

## Подтверждённые дефекты

### P1 — семейный обмен затирает успешную местную правку после заключительного чтения

Участок: `src/ui/useFamilySync.ts:317–367`, особенно безусловная запись всех объектов в строках 364–367.

1. В локальной базе препарат с остатком 10.
2. Семейный обмен получает новый анализ; вследствие этого выполняет финальное чтение и готовит `финал`.
3. До записи `финал` пользователь успешно сохраняет тот же препарат с новым названием и остатком 6.
4. Обмен пишет ранее прочитанный объект поверх местной правки, возвращая остаток 10. Затем отправляет этот откат в облако.

Результат воспроизведения: перед продолжением синхронизации `left:6`, новое имя и более свежий `updatedAt`; после — `left:10`, старое имя и старый `updatedAt` как локально, так и в отправленном JSON. Окно гонки воспроизведено задержкой порта `putTombstones` между чтением и записью; бизнес-логика и IndexedDB настоящие. Проблема существует даже когда новый облачный объект — анализ, а препарат вообще не менялся на другом телефоне.

Причина: дополнительное чтение сокращает окно гонки, но не делает read/merge/write атомарным относительно пользовательских сохранений. Переменная `идёт` блокирует только другие циклы этого hook, а не записи приложения. Потенциально затрагивает также изменения назначения, результаты анализов и отметки приёма.

Исправление: атомарная операция применения семейного изменения внутри одной readwrite-транзакции, читающая текущие объекты в этой транзакции; или единый общий сериализатор всех операций записи с повторным merge непосредственно перед фиксацией. Простого третьего чтения недостаточно.

### P2 — пользовательское сохранение анализа или измерения подтверждается, хотя объект уже удалён

Участки: `src/platform/web/storage.ts:206–211, 411–415`; вызовы `src/App.tsx:637,905`; закрытие формы анализа `src/ui/Labs.tsx:597–599`.

Открыть редактирование анализа/измерения, удалить этот же объект другим локальным действием, сохранить ввод. Для измерения достижим также конфликт с семейным удалением; для анализа именно удаление через текущий JSON-обмен блокирует отдельная ошибка D4, поэтому этот семейный путь для анализа не заявляется проверенным. Оба storage-метода молча пропускают объект с tombstone, но успешно разрешают Promise. `handleSaveLab/handleUpdate` считают запись успешной; форма анализа закрывается и черновик очищается.

Воспроизведено на действительном IndexedDB: создать → удалить → сохранить правку. Оба Promise разрешились, ни анализа, ни измерения в базе нет. Проверка UI-цепочки выполнена чтением кодового пути; полный пользовательский жест в форме с одновременным удалением отдельно не автоматизирован.

Исправление: отдельная семантика пользовательской записи, аналогичная существующему `requireWrite` у препаратов и курсов. Проверка tombstone и отказ должны быть в той же транзакции. Импорт может по-прежнему молча пропускать удалённые записи, но пользовательская форма обязана оставить введённое и объяснить конфликт.

### P2 — «Отменить удаление» не переживает получение той же отметки удаления с другого устройства

Участки: `src/platform/web/storage.ts:220–227`; `src/logic/merge.ts:294–311`; `src/App.tsx:648–656`.

1. Удалить измерение; его tombstone успевает попасть в семейный файл/на другое устройство.
2. В пределах доступных 30 секунд нажать «Отменить». Измерение возвращается, местный tombstone удаляется.
3. Снова получить файл, содержащий прежний tombstone: измерение исчезает повторно.

Воспроизведено настоящим `restoreMeasurement` и `mergeDiary`: наличие сразу после отмены `true`, после слияния `false`. В протоколе нет события отмены удаления: отсутствие tombstone не может отменить существующий tombstone у соседа. Обновления `updatedAt` само по себе недостаточно, поскольку удаление всегда побеждает.

Исправление требует согласованного протокола восстановления/отмены либо задержки распространения удаления до закрытия окна отмены. Нельзя просто разрешить любой свежей записи побеждать tombstone: это возродит удалённое из старых телефонов и импортов.

### Латентный дефект — обработчик восстановления оставляет снимки удалённого анализа (не считать подтверждённым обычным импортом)

Участок: `src/App.tsx:714–722`, ветка `grave.kind === 'lab'` в `handleRestore`.

**Уточнение 18 октября:** тест ниже напрямую передавал `ImportResult` обработчику и обходил JSON-парсер. Последующая проверка выявила, что `parseTombstones` вообще отбрасывает `kind:lab`. Поэтому эта утечка сейчас не достижима обычным импортом JSON и исключена из числа подтверждённых пользовательских дефектов. Она станет достижима после исправления парсера, если не починить удаление снимков одновременно. См. подтверждённый roundtrip-дефект в `reviews/total-audit-performance.md`.

У анализа есть снимок. Импортировать копию с tombstone этого анализа. Анализ удаляется, снимки остаются в `labPhotos`, расходуют память и больше недоступны из карточки. Обычное удаление и семейный обмен вызывают `deleteLabPhotosOf`, а восстановление его пропускает.

Воспроизведён настоящий `App.handleRestore` через наблюдающий тестовый build без изменения production: до — 1 анализ, 9 тестовых байт; после — 0 анализов, 1 осиротевший снимок, те же 9 байт. Реальный бланк может занимать существенно больше; количество потерянных байт в тесте специально минимальное.

Исправление: применить общую атомарную операцию удаления анализа и его снимков для всех путей удаления; проверить импорт, обмен и пользовательское удаление одним контрактом.

## Проверено без новой подтверждённой находки

- `mergeChangedAnything` включает новые/обновлённые анализы и изменения tombstones. Исторические дефекты не повторены как актуальные.
- Семейный hook: блокировка параллельного старта, отмена ожидания при смене аккаунта, сериализация облачных PUT между ключами, исключение старого файла после успешного нового upload.
- Настройки и пользовательские записи препарата/курса ожидают завершение транзакции; препараты/курсы отвергают tombstones для пользовательского сохранения.
- Ключ сопряжения исключается из JSON-копии и семейной отправки. OAuth-ключ и пароль резервной копии не входят в Settings-экспорт. Семейные файлы намеренно открытые; UI это поясняет.
- Android backup отключён; FileProvider не экспортирован. Полноценный security/pentest в эту функциональную проверку не входил.
- PWA: атомарная установка precache, предыдущий cache для старых lazy chunks, кеши ограничены scope. Эти ветки просмотрены; отдельный новый offline suite этим критиком не запускался.
- Updater: опубликованные релизы сортируются по версии, фильтруются по наличию APK соответствующей версии; установка повторно проверяет конкретный предложенный тег. Перебора выпусков на живом GitHub и физической установки этим критиком не было.
- Автокопия при временном отказе повторяется при следующем изменении. UI честно указывает это условие; отсутствие отдельного таймера не оформлено как дефект.
